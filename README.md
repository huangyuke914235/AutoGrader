> 评测口径：基准答案（gold set）由**不参与代码与 prompt 开发**的成员独立打分——
> 打分期间不看系统输出、不与主程讨论，完成后封存，直到评测当天才解封。
> 让写 prompt 的人同时定义「正确答案」，等于对着答案改答案。

## 核心方法论：RAG-E 四阶判定链

```
R 评分点原子化   教师用自然语言写评分标准 → 拆成可独立判定的原子评分点
A 证据锚定判定   逐评分点独立判定，必须回引报告原文；引用经代码逐字校验
G 一致性守卫     低置信自动二次复核，不一致 / 分值差距过大 / 调用失败一律转人工
E 反馈生成       基于已定稿的逐项判定生成总评与可执行改进建议
```

## 三条工程约束

1. **分数由代码加总** —— 模型只输出单点评定（hit / partial / miss 与该项分值），
   总分由代码求和；判定与分值明显矛盾时标记转人工，不会静默改分
2. **无证据的判定不算数** —— 每条引用都必须通过代码的原文**逐字匹配**校验，
   匹配不上就作废重跑（不接受模糊匹配或近似匹配）；两次都不通过则清空证据、转人工复核
3. **不确定就交给人** —— 低置信、两次判定不一致、两次分值差距过大、模型调用失败，
   全部显式标记为「待人工复核」，并在界面上单独计数

## 自评测结果（9 份真实实验报告 vs 封存的人工打分）

评测方法：**9 份**真实报告由**不参与开发的成员**独立人工打分并封存，
直到评测当天解封；系统侧走与产品完全相同的流水线。

> 另收集了 1 份篇幅超长的报告（6.8 万字），**不计入下列任何指标**，单独作为超长模式的压力测试：
> 它在"关键词召回"模式下被判 27 分（人工 43 分），其中「核心实现」整项被判 miss；
> 把全文上限提高到 7 万字、改为全文判定后升到 52 分（人工 43）。
> 结论：**看不到就判没有，会造成系统性低估**——因此现在召回模式下的所有 miss 一律强制转人工复核。
> 该份人工分保留在基准集里，但为避免事后更改评测集，主指标仍只统计预先登记的 9 份。

| 评测版本 | MAE | 误差 ≤5 分占比 | 证据可溯源率 |
|---|---|---|---|
| 缺陷 #3 修复前（**对外主指标**，保守口径） | **20.44** | 0% | 84.9% |
| 深度整改后 · 第 1 次（含一致性复核） | 6.89 | 44.4% | 97.0% |
| 深度整改后 · 第 2 次（同代码重跑） | 6.67 | 33.3% | 96.9% |

**为什么把最难看的那一行标成主指标**：20.44 那一轮跑在缺陷 #3 修复**之前**，
是这套系统在真实数据上的**下限**。后两行发生在 gold set 解封之后，
严格来说不是盲测 —— 我们无法自证没有沾到 gold 的光。
所以对外承诺用下限，把上限作为参考同时列出，由评委自行判断。

后两次是同一份代码相隔一段时间跑的完整评测，**指标落在 6.67 ~ 6.89 的区间内**，
相关系数 0.907 ~ 0.936，系统失败率 0%。对外给出区间而非单次最优值 ——
这个量级的波动，正是「AI 只出初评、教师终裁」的现实依据。

已知局限：

- 对高水平报告的区分度有限：9 份中有 4 份被判满分（另有 1 份接近满分），高分区区分度不足；
- ~~不支持图片与截图内容（无 OCR）~~ → **已支持**：`deepseek-flash`（DeepSeek-V4.1-Flash）
  可逐页读图，截图与扫描件内容会转录为可引用正文并标注页码（见下节「多模态 OCR」）；
- 超过 7 万字的报告仍走关键词召回，实测会低估（召回模式下所有 miss 已强制转人工）；
- 评语生成环节偶发输出格式失败，失败时自动退回规则兜底评语，评分与证据不受影响。

数字的复现方式：`tools/batch_run.py` + `tools/benchmark.py`。
**说明**：完整数据集（真实报告与人工打分）不在公开仓库中（含个人作业内容），
因此外部无法逐位复现这组数字。公开仓库提供了可复现的全部工具与模板：

| 产物 | 生成方式 | 用途 |
|---|---|---|
| 脱敏裁剪样例 `docs/cases/` | `tools/publish_demo.py` | 主页离线可看的评阅案例 |
| 打分表模板 [`docs/templates/gold_人工打分表_空白.xlsx`](docs/templates) | `tools/make_gold_sheet.py` | 按 README 流程在自己收集的数据上得到同口径指标 |
| 班级演示队列 `data/class_demo/cohort.json` | `tools/build_class_demo.py` | 班级学情看板的零配置演示 |

打分表模板含 5 张表（说明与纪律 / 评分点定义 / 逐项打分 / 总分汇总 / 封存记录），
评分点与公开案例、`tools/make_demo.py` 用的标准完全一致 —— 换成你自己班的报告即可复用。
（模板里只有评分点与表头，**不含任何真实分数**；含人工分的 `gold.json` 在 `data/gold/`，已 gitignore。）

> **项目定位**：教师辅助初评 + 班级学情工具，**不是**可以无人监督直接发布正式成绩的自动评分系统。
> 系统只产出带证据的初评，最终成绩由教师确认。
> 图片与截图通过多模态 OCR 读取（见「多模态 OCR」一节），但**转录可能有误**，
> 因此界面同时提供原始版面对照供人工核对，OCR 内容不参与最终裁定。

## 班级学情：从「一份报告几分」到「这个班卡在哪」

赛题方向是「AI + 教学**管理**助手」，而管理真正要回答的不是"这份报告几分"，
而是三个决策问题：**这个班普遍卡在哪、下一节课该讲什么、谁需要我找一趟。**
`classview.py` + `class_ui.py` 就是为这三件事存在的。

**分数来自模型，共性短板来自算术。** 这两件事在界面上分开讲清楚 ——
前者有波动、需要人工终裁；后者是确定性统计，可以放心拿去做教学决策。

看板给出四类东西：

- **共性短板**：逐评分点统计「拿满 / 部分拿到 / 完全缺失」与薄弱率，
  按薄弱率排序 —— 排最前面的就是最该占用课堂时间的那一项；
- **建议动作**：分「课堂教学 / 作业说明 / 评分标准 / 需人工处理」四类。
  例如某评分点多数人整项没写，建议就不是"加强练习"，而是
  *"在作业说明里把这一项写成可勾选的要求并附达标范例"* —— 整项缺失通常意味着要求没落到纸面；
- **可以直接当范例讲的报告**：教学建议里写着"用达标样本做对照"，
  没有现成样本教师还得自己去找，所以直接列出来；
- **需要关注的学生**：按总分升序，带最弱项、缺失项数、待复核数。

两条纪律由测试守着（`tests/test_classview.py`）：

1. **系统的问题不算到学生头上** —— 调用失败、召回模式强制转人工的 miss
   一律不进"学生没做到"的统计。否则教师会去讲一个其实没问题的知识点。
2. **样本不足就说样本不足** —— 有效样本 < 8 份时明确提示不要据此下
   "这个班普遍如何"的结论，而不是照样给一个百分比。

```bash
python tools/make_class_roster.py    # 生成 9 份典型形态的班级演示样本（自造内容）
python tools/build_class_demo.py     # 真实模型评阅 → data/class_demo/cohort.json
```

实测（12 份队列，含 3 份真实样本）：均分 73、区间 0~100、及格率 66.7%；
系统识别出「分析与总结」是共性短板（7/12 未拿满，均分 12.08/20）。

> 演示数据质量说明：队列里 1 份几乎只有截图占位（157 字）被判 0 分 ——
> 这正是**多模态 OCR 要解决的场景**（开启读图后它不再因为"读不到"而被判死）。
> 把这份留在队列里是有意的：班级学情里"有一个学生明显掉队"是真实分布的一部分。

## 零配置演示（不填 API Key 也能看完整个产品）

公开部署上评阅链路必须要一个模型，但**评委不该为了看一眼产品去申请密钥**。
仓库内置了预置评阅结果（`data/demo/*.json`），打开页面即可载入：
逐评分点判定、原文证据、代码加总、成绩单导出一应俱全。

```bash
python tools/build_demo.py          # 离线规则引擎生成（零成本、可复现）
python tools/build_demo.py --live --ocr   # 用真实模型 + 多模态 OCR 生成（需 LLM_API_KEY）
python tools/verify_demo.py         # 出厂检查：证据是否逐字可校验、总分是否等于各项之和
python tools/publish_demo.py --first S03  # 把已有结果发布成主页案例（脱敏裁剪，不重跑模型）
python tools/show_demo.py S03       # 人工核对某一份的判定、证据与评语
```

预置结果必须**如实标注引擎来源**：规则引擎产物会写明「未调用模型、一律转人工复核」，
不会被伪装成 AI 终评。

**主页案例与演示结果是同一次评阅**（`docs/cases/` 由 `publish_demo.py` 从
`data/demo/` 脱敏裁剪而来，正文只保留「每条证据 ±500 字」的窗口，
并通过学号/手机/邮箱扫描才允许写出）。发布脚本**不调用模型** ——
重跑会产生新结果，于是网页上的分数与 Demo 里载入的分数对不上，
而评委正好会拿这两处对照。案例列表按字母序，**默认展示哪一个由
`manifest.json` 的 `default` 字段**决定（当前是 S03：15 条证据、含一次真实的一致性复核分歧）。

> 当前仓库内的预置结果与主页案例均为**真实模型产物**（`deepseek-flash`），
> 引擎字段如实写着模型名与调用统计；用规则引擎重新生成会覆盖成「未调用模型」的标注。

## 多模态 OCR（截图与扫描件）

实验报告里最关键的证据常常是**截图**：运行结果、报错、IDE 界面、结果表格。
纯文本抽取只能拿到「运行结果示例」这行标题，正文是空的 —— 这正是旧版本
把一整类报告系统性判低的原因。

现在每一页都可以交给多模态模型读出来，产出**可引用、可审计、可缓存**的补全文本：

- **模型**：`deepseek-flash`（DeepSeek-V4.1-Flash，官方定价页标注 `Vision ✓`）；
  通道表里标了 `vision` 能力，不支持读图的模型会被界面直接禁掉，不会等到调用时报 400。
- **两种档位**：正文里没有代码/输出 → `transcribe`（全量转录，这是主要场景）；
  正文里已有代码 → `caption`（只描述图片，避免重复计分、成本更低）。
- **页码即坐标**：每页转录都带「第 N 页 OCR 转录」标题，拼进正文后由解析器切成
  **独立章节**，于是证据可以精确指到某一页，老师一眼能翻到那张截图。
- **不使用即不花钱**：结果按「文件哈希 + 渲染 DPI + 模型 + 提示词版本 + 档位」
  缓存到 `.ocr_cache/`（已 gitignore），同一份报告重复评阅只调用一次。
- **失败逐页隔离**：第 3 页读不出来不影响其余页；读不出来就写「无法辨认」，
  **绝不由代码编造一段不存在的文本**。OCR 整体失败也只是降级，评阅照常进行。

> 界面提供**原始版面对照**（PDF 渲染页图，仅内存、不落盘）供老师核对截图与公式。
> 它与 OCR 是两件事：前者给人看，后者给模型读；两者都不改学生原文。

### 读图到底改变了什么：同一份报告的对照

`tools/build_ocr_comparison.py` 造一份**内容全在截图里**的报告（正文只有
"（此处为运行截图）"这类占位说明，运行数据只存在于图片中），用**同一份报告跑两次**：

| | 不读图 | 开启读图 |
|---|---|---|
| 总分 | **4.0** | **38.0** |
| 证据条数 | 1 | 10 |
| 正文长度 | 142 字 | 980 字 |
| 「结果与数据」 | 0 / 20 | **20 / 20** |
| 「环境与步骤」 | 0 / 20 | 12 / 20 |

截图独有的四个关键值（余额 1500.00 / 1200.00、失败原因「余额不足」、操作统计
「成功 3 次」）**全部**被读出来并进入证据链。

这张表说明的不是"OCR 让分数变高了"，而是**旧版本会把一整类报告判死** ——
判 4 分不是因为学生没写，是因为系统看不到。这类假阴性比分数高低危险得多：
它会把"写了但没截好图"和"根本没做"混为一谈。

> 复现：`python tools/build_ocr_comparison.py`（需要 `LLM_API_KEY`，两次评阅共约 10 次模型调用）。
> 结果落在 `data/class_demo/ocr_comparison.json`。


## 批量测试（界面第 ⑤ 个标签页）

两种批量能力，都可以导出 CSV 留痕：

- **多份报告批量评阅**：一次跑完选中的报告，出横向对比表；
  本地存在封存的人工 `gold.json` 时，自动对齐算出 MAE / 误差≤5 分占比 / 证据可溯源率。
- **同一份报告重复评阅**：连跑 N 次，看总分极差与评分点判定稳定率 ——
  这是「G 一致性守卫」存在的实证，稳不稳用数据说话。

> 注：自定义评分点与人工 gold 的维度对不上，此时界面会**拒绝计算 MAE**，
> 因为维度不一致时算出来的误差没有意义。

## 故障排查记录

产品迭代过程中修掉的三个真实缺陷，都保留了完整的定位与验证过程：

- [反馈生成失败](docs/bugfix-反馈生成失败.md) —— 异常被 `except` 吞掉，线上查不到原因
- [引用匹配与 PDF 断行](docs/bugfix-引用匹配与PDF断行.md) —— 引用对不上原文，评分点被误判为 0 分

## 隐私与数据说明

- 本仓库**不包含**任何原始实验报告。`data/` 目录已在 `.gitignore` 中，原始文件只保留在本地。
- 主页 `docs/cases/` 中的演示案例做了双重处理：**全文脱敏**（学号 / 姓名 / 班级 / 电话 / 邮箱均替换为占位符并做残留扫描）
  + **裁剪为证据片段窗口**（每条证据前后各保留 500 字），不含完整作业原文。
- 脱敏脚本本身**不包含任何真实姓名与本机路径**：样本清单与已知姓名从本机配置文件读取，
  该配置已在 `.gitignore` 中（仓库内只提供模板）。
- 上传的报告写入受控临时目录（UUID 文件名，不参与任何路径拼接）。
  失败路径**立即删除**；成功路径保留到「下一次上传」或超期清扫 ——
  保留是因为多模态 OCR 需要按页渲染原件才能读截图（见 `app.sweep_stale_uploads`）。
  结果文件名使用随机 ID，上传文件不会长期留存。
- **原始版面对照**：PDF 报告会在页面内渲染出原始页面图（最多前 20 页，只在内存中、不落盘），
  方便教师在界面里直接核对截图、图表与公式。
- **多模态 OCR 的隐私边界**（必须说清楚）：开启读图后，页面图片会被发送到模型服务；
  OCR 缓存写入 `.ocr_cache/`（已 gitignore，只在本机/服务器本地，不随仓库发布）。
  公网部署下评阅结果仍然**不落盘**，OCR 缓存是唯一的本地写入项，
  它采用文件内容哈希命名、不含学生信息，且可由管理员随时删除。
