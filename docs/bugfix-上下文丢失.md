# Bugfix：判定阶段上下文丢失，导致系统性假阴性

> 这份文档记录我们靠 **gold set 人工评分** 发现的一个严重缺陷。
> 它不是调参记录，而是一个纯工程 bug 的定位与修复过程。
> 如实保留修复前后的指标对比，包括这次修复是在 gold 解封之后才定位到的事实。

---

## 一、现象：第一次 benchmark 结果很难看

B 成员完成 10 份报告的人工打分（gold set 封存）后，跑 `tools/benchmark.py`：

```
MAE 平均绝对误差：31.67 分
误差 ≤5 分占比  ：11.1%
证据可溯源率    ：94.9%（93/98 条引用通过原文精确匹配）
```

逐份对比显示，**9 份里有 8 份系统评分低于人工分**，其中 S07/S08/S09 差了 48–54 分：

| 报告 | 人工 | 系统(v1) | 差 |
|---|---|---|---|
| S01 | 96 | 45 | −51 |
| S02 | 49 | 22 | −27 |
| S03 | 81 | 82 | +1 |
| S04 | 93 | 67 | −26 |
| S05 | 90 | 82 | −8 |
| S07 | 63 | 12 | −51 |
| S08 | 93 | 39 | −54 |
| S09 | 95 | 47 | −48 |
| S10 | 95 | 76 | −19 |

**8/9 单方向低估** —— 这不是随机误差，是系统性偏差，一定有具体原因。

判定分布对比更刺眼：

| | hit | partial | miss |
|---|---|---|---|
| 系统 v1 | 15 | 17 | **13** |
| 人工 | 36 | 9 | **5** |

系统判的 miss 是人工的 2.6 倍，且集中出现在 **r3 核心实现**（25 分，最大项）。

## 二、是不是报告里真的没有内容？—— 先证伪

假设之一是"这些报告确实写得差，人工打分太松"。验证办法很简单：把系统判 miss 的项拿回原文搜关键词。

| 报告 | 系统判定 | 原文实际情况 |
|---|---|---|
| S01 | r3 核心实现 = miss | 含「print」×44、「图」×46、「输出」×29、「运行结果」×17 |
| S08 | r3 = miss | 含「表」×26、「图」×16 |
| S09 | r3、r4 = miss | 含「表」×22、「结果」×10、「输出」×6 |
| S04 | r3 = miss | 含「表」×17、「输出」×6 |

**内容明明都在。** 排除"报告真的没写"和"人工打分过松"。

## 三、根因：模型只看到了报告的 7%~11%

顺着 `pipeline.stage_judge` 往下查，发现问题在这一行：

```python
picked = P.retrieve(sections, item.positive_signals, top_k=top_k)      # top_k = 4
ctx = "\n\n".join(f"[{s.id}] {s.title}\n{s.text[:2500]}" for s in picked)
```

只取召回分数最高的 **4 个章节**，每个再截断到 **2500 字**。

而 `parser.split_sections` 为了保留结构，会把报告切得相当碎 —— S01 一篇被切成 **149 个章节**。碎章节 + top_k=4 的结果是：

| 报告 | 全文字数 | 章节数 | 实际送进模型 | 模型看到 |
|---|---|---|---|---|
| S01 | 24,966 | 149 | 1,709 字 | **7%** |
| S08 | 5,351 | 33 | 594 字 | **11%** |
| S09 | 9,213 | 46 | 1,054 字 | **11%** |

模型拿着报告的十分之一去判定"有没有核心代码/运行结果"，判 miss 完全合理。
**这不是模型能力问题，是我们的工程缺陷。**

讽刺的是，`parser.py` 里其实早就写好了修正方案 `build_context()`（小文档给全文，超长才召回），
但 **`git grep build_context` 显示它从来没有被任何地方调用过** —— 修复方案写了，却没接上。

这正是 D2 踩过的第三个坑（"召回切碎文档导致假阴性"）的残留。

## 四、修复

`pipeline.py` 两处（`stage_judge` 判定阶段、`stage_consistency` 一致性守卫）都改走自适应上下文：

```python
# 修复前
picked = P.retrieve(sections, item.positive_signals, top_k=top_k)
ctx = "\n\n".join(f"[{s.id}] {s.title}\n{s.text[:2500]}" for s in picked)

# 修复后
ctx, _is_full = P.build_context(sections, full_text, item.positive_signals, top_k=top_k)
```

`build_context` 的逻辑：`len(full_text) <= 40000` 时直接返回全文（正确性优先），
超长才退化为召回。取舍是 token 成本上升，我们选择为正确性买单。

**没有改动任何 prompt。** 三条铁律（分数由代码加总、无证据不算数、不确定交给人）保持不变。

## 五、修复效果

改完之后在同一份 gold set 上重跑（`tools/batch_run.py` → `tools/benchmark.py`），
gold 分数一行未改：

| 指标 | 修复前 v1 | 修复后 v2 | 变化 |
|---|---|---|---|
| **MAE 平均绝对误差** | 31.67 分 | **13.33 分** | ↓ 58% |
| 误差 ≤5 分占比 | 11.1% | **22.2%** | ↑ 2 倍 |
| 证据可溯源率 | 94.9% | **95.1%** | 持平（铁律未放宽） |
| 评分点判定一致率（内部参考） | 42.2% | **73.3%** | ↑ 74% |

逐份对比也从"8/9 单方向低估"变成正负分布：

| 报告 | 人工 | v1 | v2 | v1 差 | v2 差 |
|---|---|---|---|---|---|
| S01 | 96 | 45 | 70 | −51 | −26 |
| S02 | 49 | 22 | 32 | −27 | −17 |
| S03 | 81 | 82 | 86 | +1 | +5 |
| S04 | 93 | 67 | 90 | −26 | **−3** |
| S05 | 90 | 82 | 75 | −8 | −15 |
| S07 | 63 | 12 | 75 | −51 | **+12** |
| S08 | 93 | 39 | 100 | −54 | **+7** |
| S09 | 95 | 47 | 80 | −48 | −15 |
| S10 | 95 | 76 | 75 | −19 | −20 |

### 到此为止，不再往下调

修复后的 MAE 13.33 依然称不上"准"。但**我们不再为降低 MAE 做任何改动**：

- 继续改 prompt 让它更貼近 gold = 对着答案改答案，正是纪律文件第一条禁止的事；
- 剩下 13 分的差距，一部分是 rubric 粒度的天然分歧（同一份报告两位助教也未必一致），
  一部分是 25 分大项（核心实现）的判定确实见仁见智；
- 这两个话题写进 PPT 的"局限性与下一步"，比偷偷改到更好看要体面得多。

我们选择报告一个带着局限的真实数字。

## 六、诚实说明

必须写清楚，否则这份文档本身就变成自欺：

1. **这次修复发生在 gold set 解封之后** —— 是看到糟糕的 MAE 才去查，才查出来的。
   它不算严格意义上的"盲测通过"。
2. 但它的性质是**客观缺陷修复**，不是"对着答案调分"：
   - 没有任何 prompt 被修改（这是纪律里最敏感的部分）；
   - 根因可被独立复现（送进模型的字数从 7% 变成 100%，任何人都能验证）；
   - 修复来自代码审查，不是来自把答案往回推。
3. 修复前的结果我们完整保留在 `data/results/batch_v1_bug.json` 与
   `benchmark_v1_bug.json`，随时可复核。

## 七、这件事证明了什么

**gold set 是有用的，而且有用得很具体。**

如果没有那份独立的人工打分，我们只会看到"系统给每份报告打了一个分数，看起来挺合理"，
demo 跑得通、案例看得漂亮，然后捧着一个 MAE 30+ 的系统去参赛，自己却不知道。

是那 50 行人工分数逼出了一个"模型只看到 10% 内容"的严重缺陷。
这比一个漂亮的数字更有价值 —— 也正好回答了"为什么要费那么大力气做独立 gold set"。
