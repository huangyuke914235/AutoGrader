# API 接入现状与「不接 API 标不标准」

日期：2026-09-24

---

## 一、结论先说

**接了**，但**当前运行环境没配密钥**，所以实际只有 8/12 项在跑。

**不接 API 确实不标准** —— 但缺的不是"精度"，是**整整一个维度**：
规则只能查"形"（有没有这个章节、格式对不对），查不了"神"
（原理讲得对不对、数据处理成不成立、误差分析有没有依据、结论是否被数据支撑）。

而"神"恰好是实验报告的含金量所在。

## 二、12 项的来源划分

| # | 检查项 | 权重 | 执行者 | 判的是什么 |
|---|---|---|---|---|
| 1 | 结构与完整性 | 10 | 规则（离线） | 8 个语义槽齐不齐 |
| 2 | 实验目的 | 6 | 规则（离线） | 有没有、写没写清楚 |
| 3 | 步骤可复现性 | 10 | 规则（离线） | 有没编号步骤 / 环境参数 |
| 4 | 原始数据表 | 10 | 规则（离线） | 有没有真实数据行 |
| 5 | 有效数字 | 6 | 规则（离线） | 小数位是否一致 |
| 6 | 单位与量纲 | 4 | 规则（离线） | 数字带没带单位 |
| 7 | 图表规范 | 6 | 规则（离线） | 图有没有编号和标题 |
| 8 | 引用与格式 | 6 | 规则（离线） | 有没有参考文献 |
| 9 | 原理阐述 | 8 | **AI** | 原理是否结合本实验，还是整段抄书 |
| 10 | 数据处理与计算 | 12 | **AI** | 计算过程是否成立、有没有跳步 |
| 11 | 误差分析 | 12 | **AI** | 误差来源是否具体、有没有依据 |
| 12 | 结论与讨论 | 10 | **AI** | 结论是否被数据支撑 |

**规则 58 分，AI 42 分。**

## 三、不接 API 的真实损失

### 1. 42% 的权重缺席

未检测项从总分分母剔除（不当 0 分，这是硬约束），所以界面上的总分
实际只按 58 分权重归一化。

### 2. 最典型的误判：给"格式漂亮但内容空洞"的报告虚高分

一份把原理整段抄教材、数据处理只写"经计算得…"、误差分析写"存在人为误差"的报告：

| 维度 | 规则项判定 | 现实 |
|---|---|---|
| 结构与完整性 | 8/8 章节齐全 → 高分 | ✅ 确实齐全 |
| 原理阐述 | **判不了** | ❌ 整段抄书，没结合本实验 |
| 数据处理与计算 | **判不了** | ❌ 跳步，看不出怎么算的 |
| 误差分析 | **判不了** | ❌ "人为误差"是万能套话 |

结果：**不接 API 时这份报告能拿高分，接了 API 会显著下降。**
这就是"不标准"的具体含义 —— 不是分数算错，是**该扣的分扣不下去**。

### 3. 规则项本身也不是万能的

它只能识别"有/没有"，识别不了"对/错"：
- 「数据记录」下面填了一堆数字 → 规则判通过，但数字是不是编的，规则看不出来
- 「误差分析」写了三行 → 规则判通过，但写的是不是套话，规则看不出来

---

## 四、反过来：不接 API 反而更稳的地方

**不要神化 API。** 当前 8 项规则不接 API 是有意为之，不是偷懒：

1. **可复现** —— 学生"改完再测"，规则项分数变化完全可信，不会被模型抖动污染。
   如果 12 项全交给模型，改一个字分数跳 5 分，反馈就失去可信度了。
2. **零成本、零延迟** —— 规则项瞬时出结果。
3. **可解释** —— 每一条判定都能指出是哪一行、哪个正则命中的，模型做不到这个精度。

所以正确的问题不是"要不要接 API"，而是"**哪些该交给 API**"。
现在的设计是规则打底 + AI 补充，这个分工不动。

## 五、接入方式

### 1. 配置（OpenAI 兼容协议，换供应商只改这三个变量）

复制 `.env.example` 为 `.env`：

```bash
LLM_API_KEY=sk-xxxxxxxxxxxxxxxx
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
DEMO_MODE=false
```

密钥走环境变量或 `st.secrets`，**不进代码、不进 Git**。

### 2. 自检当前配置

```bash
python tools/check_api_status.py
```

会打印：API 配没配、12 项里哪些能出分、实际计分权重是多少、连通性实测。

### 3. 三种模式的用途

| 模式 | 配置 | 覆盖 | 适用场景 |
|---|---|---|---|
| 演示模式 | `DEMO_MODE=true` | 8 项（58 权重） | 答辩排练、离线演示、不花钱 |
| **缺密钥** | `DEMO_MODE=false` 但无 key | 8 项（58 权重） | ⚠️ 等同于演示模式，界面已明示 |
| 完整模式 | key + base_url 都配好 | 12 项（100 权重） | 真实使用 |

### 4. 成本量级（DeepSeek 参考）

一份报告约 2–3k token，单次诊断约 ¥0.01 量级，1000 份在**十元级**。
学生反复"改完再测"是主要消耗来源，必要时可加节流。

## 六、本轮顺带修的一个真实缺陷

**问题**：`DEMO_MODE=false` 但没配密钥时，界面上**不会有任何提示** ——
42% 的权重静默缺席，使用者会把"只跑了 8 项"当成"跑了 12 项"。
这比不接 API 本身更危险，因为它制造了虚假的完整性。

**修复**：

1. `llm.py` 新增 `ai_ready()` / `ai_blocked_reason()` —— 判断 AI 是否**真的**能出分，
   而不只是"DEMO_MODE 关没关"。
2. 自检 Tab 顶部：AI 不可用时直接警告
   `当前只有 8/12 项在计分：{原因}`，并说明这 4 项判不了什么。
3. 结果区：分母不再无脑写 100，改为
   `本次实际计分权重 58 / 100 —— 4 项未检测已从分母剔除`，
   并标注"这个分数只覆盖格式与结构维度，不覆盖内容正确性"。

**原则**：宁可明说"我只查了一半"，不可让人以为"我全查了"。
这与"系统错误 ≠ 学生没做到"是同一条纪律的另一个面。

## 八、风险与待确认

1. **AI 项有随机性** —— 同一份报告两次调用可能差几分。当前 `temperature=0.2`
   已压低，但版本对比时仍可能把抖动误读成"进步/退步"。
   （已知风险，未做稳定性加固。）
2. **成本不可控** —— 学生反复体检无节流。需确认要不要加每日次数上限。
3. **数据出境** —— 报告正文会发给模型供应商。若学校有数据不出校要求，
   需改用本地/私有化模型（`LLM_BASE_URL` 指向校内推理服务即可）。
   **这一条需要提前确认，不能等上线了才发现。**
4. **AI 判错无人兜底** —— 学生端没有教师复核环节，AI 误判会被学生直接接受。
   建议：体检分明确标注"仅供参考，与教师正式评分无关"（已在界面写明）。
