# 缺陷复盘 #3：引用匹配不上原文，11 个评分点被误判为 0 分

> 这是三轮修复里最容易被误读的一处：**修完分数一定上升，而且是在基准集解封之后修的**。
> 因此本文除了技术过程，也用一节专门说明"这算不算放宽规则让数字变好看"。
> 对外主指标仍取修复前的 20.44，而不是修复后的数字。

---

## 1. 现象

完整重跑一次评测（`tools/batch_run.py` → `tools/benchmark.py`），结果比上一轮差很多：

| 指标 | 上一轮 | 本轮 |
|---|---|---|
| MAE 平均绝对误差 | 13.33 | **20.44** |
| 误差 ≤5 分占比 | 22.2% | **0.0%** |
| 证据可溯源率 | 95.1% | **84.9%**（135/159） |

逐份看：人工 93 / 95 / 95 的 S08 / S09 / S10，系统只给了 60 / 60 / 55；
而 S08 在上一轮跑分里是 100 分。

## 2. 排查

第一步先排除"是不是前一天新增的 JSON 宽容解析把引用改坏了"。
做法：把新旧两批 `batch.json` 的每一条 quote 拿回原文匹配，并按失败原因分类统计。

结论：**不是 JSON 修复引起的**。失败的引用里没有转义残留、也没有被截断的痕迹，
而且新旧两批存在完全相同的失败样本（例如 S09/r5、S10/r3），说明问题一直存在。

真实原因有两类，都很具体：

### 根因一：PDF 抽取把正文切得满是断行

| 报告 | 来源 | 平均每隔多少字一个换行 |
|---|---|---|
| S08 / S09 / S10 | PDF | **18.9** |
| S01 | DOCX | 25.3 |

PDF 转出的文本几乎每行都被斩断。模型看到的是
「客户端 Windows 上的 VDS 3.9，路径 D:\VDS\VDS.exe」这样通顺的句子，
而原文里这句话中间夹着换行与多余空格 —— **逐字匹配必然失败**。

典型失败样本（去掉空白差异后即可匹配）：

```
[S08/r2] "客户端 Windows 上的 VDS 3.9，路径 D:\VDS\VDS.exe"
[S09/r2] "所有脚本固定 SEED=42，并输出 JSON 指标、CSV 预测和数据元信息。"
[S10/r4] "最终平均交叉熵 0.008738"
```

如果把正文与引用**同时**做空白归一（两侧用同一套规则），本批次的可溯源率为
**155/159 = 97.5%**，而不是 84.9%。

### 根因二：短引用"一票否决"整条判定

`verify_evidence` 中有一条 `min_len = 6`：引用短于 6 个字即判不合法。
本批次有 10 条这样的引用：

```
'实验感想'  '实验建议'  '程序代码'  '设计思路'  '类设计说明'
'运行结果'  '截图说明'  '优点：'  '缺点：'  '执行失败。'
```

问题不在这些引用本身 —— 它们确实是原文中的章节标题。
问题在**处理方式过粗**：一条不合格，就把整条判定连同另外 3 条合格证据一起作废。

### 后果：11 个评分点被判 0 分

本批次有 **11 个评分点**走完"两次引用都未通过 → 降级 miss + 待复核"的路径，分数直接归零。
而它们附带的证据在报告里确实存在：

| 报告/评分点 | 系统判定 | 它引用的证据（真实存在于报告中） |
|---|---|---|
| S08 / r2 环境与步骤 | 0 分 | VDS 客户端路径、远程数据库连接、SELECT 语句 |
| S09 / r5 分析与总结 | 0 分 | 三分类任务定义、典型错误清单、跨场景迁移结论 |
| S10 / r3 核心实现 | 0 分 | 单层 tanh RNN 代码、前向/反向公式 |
| S02 / r3 核心实现 | 0 分 | 「程序代码」「设计思路」等章节标题 |

也就是说：**这套机制在惩罚"报告写得好、模型引用得多"的报告** ——
引用越多，越容易撞上一条不合格的引用，整条判定就越容易被清零。

## 3. 这算不算"放宽规则让数字变好看"？

这是必须正面回答的问题。

结论是：这两处属于**工程缺陷修复**，不属于放宽规则。理由：

- **空白归一改的是输入端**。PDF 抽取产生的换行是抽取产物，不是报告内容；
  正文与引用**两侧用同一套规则**规范化后仍是精确匹配，不是模糊匹配或近似匹配。
- **"一条短引用否掉整条判定"改的是判定粒度**，不是判定标准：
  改成"逐条校验、剔除不合格的那条，只要还剩合格证据即通过"，
  而被保留的每一条引用，仍然必须在原文中逐字存在。

同时必须交代：**两处修完，分数一定上升，而且修复发生在基准集解封之后。**

区别在于修复动机：驱动这两处修改的是"系统性地低估"这个**方向性信号**，
不是逐条对照人工分数去调参（后者才是对着答案改答案）。
但时序上晚于解封，**这一轮结果不构成严格盲测**。
唯一的交代办法是如实披露，并把修复前的 20.44 保留为对外主指标，
而不是用新数字覆盖旧数字。

## 4. 实际改动

| # | 位置 | 改动 |
|---|------|------|
| 1 | `parser.canonical()` / `parse_file()` | 正文统一空白归一（`re.sub(r"\s+", " ", text)`）。章节切分仍在**原始文本**上进行（识别标题需要换行），切分后再各自归一、并按归一文本重算 `char_start/char_end`，保证详情页定位不错位 |
| 2 | `llm.verify_evidence()` | 改为**逐条**判定：剔除不合格引用，只要还剩至少一条合格引用即判定成立；保留的引用仍须逐字存在于原文；被剔除的写进 `reason` 留痕 |
| 3 | `models.ItemJudgement.dropped_quotes` | 新增字段（模型不输出），专门记录被剔除的引用 |
| 4 | `tools/batch_run.py` | 明细中增加 `dropped` 字段 |
| 5 | `tools/benchmark.py` | 正文改用 `parser.canonical` 后再匹配；被剔除的引用计入分母且记为不可溯源 —— **保证可溯源率按"模型原始产出"计算，不因筛选而虚高** |
| 6 | `app.py` / `batch_ui.py` | 原本绕过解析入口直接读文本的两处，统一改走 `parse_file`，避免界面与批量评测使用的正文不一致 |

## 5. 验证

- 上一轮 14 条失败引用中，空白归一救回 **9 条**（S08 3/3、S10 4/5、S09 2/5）；
  其余 5 条属于模型自行改写（例如把 SQL 重排了格式），现在会被**逐条剔除**，不再拖累整条判定。
- 章节偏移自洽性检查：33 个章节全部能在归一文本中找到，偏移单调递增。
- 修复后又发现了本次归一引入的一个不对称问题（正文归一了、引用没归一，
  导致多行代码块引用永远匹配不上），已同步修复 —— 详见仓库提交记录。
- 后续还有一轮深度整改，最终指标见主页与 README。

## 6. 结论

发现问题是本事，承认修完会涨分也是本事，两件事都要做到。
修复前的 20.44 与修复后的数字并列展示，取舍说明写在主页显著位置，
由评委自行判断这个区间是否可信。
