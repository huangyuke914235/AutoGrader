# 缺陷复盘 #2：线上「反馈生成失败」的定位与修复

> 现象是页面底部显示「反馈生成失败」，根因是异常被吞掉 + 模型输出的 JSON 不合法。
> 这篇记录完整链条：从最初错误的判断，到真凶，到五层防护与兜底。

---

## 一、现象

部署到 Streamlit Cloud 后，用户跑了一次评阅：

- 评分点、得分、置信度、待复核标记 —— **全部正常**
- 页面底部「评语与改进建议」—— **（反馈生成失败，请查看逐项判定）**

即占分 100 的部分没事，唯独最后一步 E（反馈生成）失败。

## 二、最初判断是错的

第一反应是"云端网络抖动 / 限流"，依据是本地连测三次 E 阶段全部成功。

这个推理有个漏洞：**本地三次的输入与线上那次不同。**
本地用的是精简后的判定串（约 880 字），线上跑的是真实报告产生的完整判定明细。

让判断翻案的，是另一个功能的界面冒烟脚本（`AppTest`，无浏览器跑 Streamlit）。
它本来只用来验证"批量测试"标签页能否运行，结果在真实调用里复现了同一个异常：

```
[pipeline] E 阶段反馈生成失败：RuntimeError: 模型输出连续 3 次未通过校验：
1 validation error for Feedback
  Invalid JSON: expected `,` or `]` at line 1 column 2351
```

**真正的原因是：模型输出的 JSON 本身不合法，连续三次都没能通过解析。**
`expected ',' or ']'` 说明解析器正处在某个数组（`suggestions`）里、遇到了不该出现的字符 ——
最典型的情形是模型在字符串内部写了**未转义的半角引号**
（例如建议里写「把"运行结果"贴到正文里」）。

经验：**「本地跑通了」不能用来否定「线上有缺陷」**；要复现线上，必须复刻线上的输入。
这次是顺手做的功能测试碰巧炸出真凶，属于运气而非本事 ——
所以后续加了 `_stats.json_repaired` 计数器，把这类问题变成可观测的数字。

## 三、三处自身缺陷

| # | 位置 | 缺陷 | 后果 |
|---|------|------|------|
| 1 | `llm.call_json` | 模型调用只捕获 `TypeError`，其余异常（连接 / 超时 / 限流 / 5xx / 余额）直接穿透且不重试 | 一次网络抖动即打挂整个阶段 |
| 2 | `pipeline.stage_feedback` | `except Exception` 吞掉一切，返回一句固定文案 | 异常原因完全不可见，只能猜 |
| 3 | 解析链路 | 输出稍不合 JSON 规范即整段报废；三次重试喂给模型的是同一句笼统提示 | 模型不知道错在哪，重试等于重造同一个错 |

三者叠加的效果是：**系统出了错，但系统不知道自己错在哪。** 这比出错本身更严重。

## 四、修复

### 4.1 传输层：异常退避重试

```python
except Exception as e:
    last_err = e
    if attempt < retries:
        wait = backoff * (2 ** attempt)        # 3s → 6s
        print(f"[llm] 第 {attempt+1} 次调用失败（{type(e).__name__}），{wait:.0f}s 后退避重试")
        time.sleep(wait)
        continue
    raise RuntimeError(f"模型调用连续失败 {retries+1} 次（{type(e).__name__}）：...")
```

带 `_stats.failed` 计数，失败原因带异常类型名上抛。

### 4.2 解析层：`loads_json` 五级降级（只修格式，不改内容）

| 级别 | 手段 | 针对的情形 |
|------|------|-----------|
| ① | 严格 `json.loads` | 正常输出 |
| ② | `strict=False` | 字符串内含未转义换行等控制字符 |
| ③ | `escape_inner_quotes` | 字符串内写了未转义的半角引号（本次真凶） |
| ④ | `close_truncated` | 输出被 `max_tokens` 截断，补齐未闭合的引号与括号 |
| ⑤ | `salvage_truncated` | 结构破损到前四级都救不回时，取能解出的前半段 |

**五步都不删改内容**：转义只是让同一个字符合法化，截断只丢尾部。
单测中有断言盯着这一点：修复后解析出的 `summary` 里，半角引号仍在、原文片段仍在。

### 4.3 E 阶段：结构简化重试

完整版提示失败后，改用**只有两层结构的简化提示**重试一次（少一层嵌套，出错面更小）。
两条路径都不影响分数与证据 —— E 阶段的输入是已经定稿的判定。

### 4.4 兜底层：失败不再静默

- `Feedback` 增加 `generated_by` / `error` 两个字段（有默认值，不影响校验）；
- E 阶段失败时：打日志 → 错误写进 `error` → 由**代码**按已锁定的判定拼装评语；
- 界面弹出黄色告警，把真实原因写给用户：
  「AI 反馈生成环节失败，以下评语由规则引擎生成……失败原因：RuntimeError: …」。

### 4.5 可观测

`_stats` 增加 `json_repaired`；批量测试页页脚显示
「本次会话累计：模型调用 N 次，调用失败 M 次，其中 K 次的输出依靠 JSON 修复才解析成功」。
这类问题从此有数字可查。

## 五、这些修复为什么不影响评分可信度

- **总分仍由代码加总**：E 阶段的输入是已定稿的判定，兜底评语不产生任何分数；
- **证据校验一字未动**：`verify_evidence` 的原文逐字匹配没有任何改动，修好的引用照旧要过这道闸门；
  单测专门验证了"被修复解析出来的引用，若对不上原文依然会被判死并重跑"。
  这里放宽的是**格式**，不是**证据**；
- **复核标记逻辑未动**：低置信、两次不一致的判定规则没有任何变化。

兜底评语的代码里还有三条断言盯着自己：分数数组未变、`evidence.quote` 未变、错因必须带真实异常类型名。

## 六、残留风险（如实列出）

1. **该缺陷未被彻底消除，仍是偶发。** 修复后的两轮完整评测中，
   第一轮 9 份里出现 2 次、第二轮 0 次，均表现为 `Expecting ',' delimiter` 一类解析失败。
   因此对外表述为"从必现降为偶发"，而不是"已修复"。
2. **失败不再静默**：一旦发生，异常类型、错误内容会写进 `Feedback.error` 字段并在界面显示，
   同时自动退回规则兜底评语。
3. **对指标无影响**：E 阶段不参与打分、不产生证据，三处对外指标（MAE、误差≤5 占比、证据可溯源率）
   与评语生成是否失败无关 —— 这一点可由 `tools/batch_run.py` 的输出验证。
