# bugfix #2：线上「反馈生成失败」——一次被自己写的代码骗过去的排查

> 这篇记录和 `bugfix-上下文丢失.md` 是同一系列：**把踩过的坑连同错误结论一起留下来**。
> 竞赛材料里凡是要吹「我们怎么发现问题的」，依据都是这两篇，而不是记忆。

---

## 1. 现象

部署到 Streamlit Cloud 之后，用户跑了一次评阅：

- 评分点、得分、置信度、待复核标记 —— **全部正常**
- 页面最下方「评语与改进建议」—— **（反馈生成失败，请查看逐项判定）**

也就是：占分 100 的那部分没事，唯独最后一步 E（反馈生成）挂了。

---

## 2. 我给出的第一个结论是错的

第一时间我判断是「云端网络抖动 / 限流」，理由是本地连测三次 E 阶段全部成功。

这个推理有个致命漏洞：**本地三次用的输入，和云端那次不一样。**
本地我喂的是精简后的判定串（约 880 字），而线上跑的是真实报告产生的完整判定明细。

真正让我翻案的是给新功能写的界面冒烟脚本（`AppTest` 无浏览器跑 Streamlit）。
它只是在验证「批量测试」标签页能不能跑，结果在真实调用里**当场复现了同一个异常**：

```
[pipeline] E 阶段反馈生成失败：RuntimeError: 模型输出连续 3 次未通过校验：
1 validation error for Feedback
  Invalid JSON: expected `,` or `]` at line 1 column 2351
```

**真实原因是：模型吐出来的 JSON 本身不合法，连续三次都没能通过解析。**
`expected ',' or ']'` 说明解析器当时正处在某个数组（`suggestions`）里，遇到了一个不该出现的字符 ——
最典型的就是模型在字符串里写了**没转义的半角引号**（比如建议里写「把"运行结果"贴到正文里」）。

教训：**不要用「本地跑通了」来否定「线上有 bug」**。
要复现线上，就得复刻线上的输入。这次是「顺手做的功能测试」把真凶炸出来的，属于运气，不是本事——
所以后面加了 `_stats.json_repaired` 计数器，把这类事变成有数字可查的东西。

---

## 3. 三处都是我们自己写出来的缺陷

| # | 位置 | 缺陷 | 后果 |
|---|------|------|------|
| 1 | `llm.call_json` | 模型调用只捕获 `TypeError`，其余异常（连接 / 超时 / 限流 / 5xx / 余额）**直接穿透，且不重试** | 一次抖动就把整个阶段打挂 |
| 2 | `pipeline.stage_feedback` | `except Exception` 吞掉一切，返回一句固定文案 | 异常原因彻底不可见，只能猜 |
| 3 | 解析链路 | 模型输出只要稍不合 JSON 规范就整段报废；三次重试喂给模型的是同一句笼统提示 | 模型不知道自己错在哪，重试等于重造同一个错 |

这三处叠在一起的效果是：**系统出了错，但系统自己不知道出了什么错。**
这比出错本身严重得多。

---

## 4. 修复内容

### 4.1 传输层：异常退避重试（不再一次失败就放弃）

```python
except Exception as e:
    last_err = e
    if attempt < retries:
        wait = backoff * (2 ** attempt)        # 3s → 6s
        print(f"[llm] 第 {attempt+1} 次调用失败（{type(e).__name__}），{wait:.0f}s 后退避重试")
        time.sleep(wait)
        continue
    raise RuntimeError(f"模型调用连续失败 {retries+1} 次（{type(e).__name__}）：...")
```

带 `_stats.failed` 计数，失败原因带异常类型名抛给上层。

### 4.2 解析层：`loads_json` 四级降级（只修格式，不改内容）

| 级别 | 手段 | 针对的语病 |
|------|------|-----------|
| ① | 严格 `json.loads` | 本来是好的 |
| ② | `strict=False` | 字符串里含未转义换行等控制字符 |
| ③ | `escape_inner_quotes` | 字符串里写了未转义的半角引号（本次凶手） |
| ④ | `close_truncated` | 输出被 `max_tokens` 截断，补齐未闭合的引号与括号 |

**四步一个字符都不删改**，转义只是让同一个字符合法化。单测里有断言盯着这点：
修复后解析出的 `summary` 里，半角引号仍在、原文片段仍在。

### 4.3 兜底层：E 阶段失败不再假装没事

- `Feedback` 增加两个字段（`generated_by` / `error`，都有默认值，不影响原有校验）
- E 阶段失败时：打日志 → 错误写进 `error` 字段 → 由**代码**按已锁定的判定结果拼装评语
- 界面弹出黄色告警，把真实原因写给用户看：「AI 反馈生成环节失败，以下评语由规则引擎…失败原因：RuntimeError: …」

### 4.4 可观测

`_stats` 增加 `json_repaired`；批量测试页页脚显示
「本次会话累计：模型调用 N 次，调用失败 M 次，其中 K 次的输出靠 JSON 修复才解析成功」。

今后「有多少是靠修复救回来的」是一个能报出来的数字，而不是一个传说。

## 5. 为什么这些修复不违反我们的三条铁律

- **铁律一**：总分仍由 `pipeline` 的代码加总。E 阶段拿到的输入是已经定稿的判定，兜底评语不产生任何分数。
- **铁律二**：`verify_evidence` 的原文逐字匹配**一字未动**。
  修复发生在「能不能把模型输出读成 JSON」这一步，之后 quote 照旧要过原文精确匹配。
  单测专门验证了：**修歪了的引用依然会被这道闸门判死并重跑**（`verify_evidence` 返回 False）。
  换句话说，这里放宽的是**格式**，不是**证据**——两件事不能混为一谈。
- **铁律三**：低置信 / 两次不一致的标记逻辑没有任何改动。

另外，兜底评语的那段代码里写了三条硬断言盯着自己：
分数数组未变、`evidence.quote` 未变、错因里必须带真实异常类型名。

## 6. 必须承认的未验证事项（不许含糊过去）

1. **修复没有在真实 API 上复测。** 开发沙箱在会话中途彻底断网（`WinError 10061`，curl 直连返回 000），
   之后再没能连上。上面 6 个用例是**人工构造的坏样本**，覆盖了包括本次错误信息在内的四类常见坏 JSON，
   但不能等同于「抓到并修好了那一个具体回包」。
2. **主页 METRICS（MAE 13.33 / 误差≤5 占比 22.2% / 证据可溯源率 95.1%）产出于本次修复之前。**
   已核查旧批次 `data/results/batch.json`：45 条判定里 **0 条** confidence 为 0，
   说明当时没有出现「整段解析失败被降级」的行。
   但无法确认其中是否有判定是靠 retry 才成功的 —— 而 retry 的结果与 repair 的结果可能不完全一致。
3. **因此联网后必须重跑**：

```bash
python tools/batch_run.py       # 重新出系统分
python tools/benchmark.py       # 重新算三个对外指标
```

**若三项指标发生变化，就按新数字更新 `docs/index.html` 的 `METRICS`，绝不沿用旧数字。**
这一条是纪律，不是礼貌。
