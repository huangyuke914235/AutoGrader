# bugfix #3：引用匹配不上原文，把 11 个评分点活活判成了 0 分

> 状态：**已定位并按方案 C 实施修复（2026-09-22 上午）**。
> 方案 C = 对外主指标挂**修复前**的 20.44（当前系统的真实水平），
> 另附一处「缺陷修复后复测：X 分」，并注明修复时间与动机。
> 修复后的数字以 `tools/batch_run.py` + `tools/benchmark.py` 重跑结果为准，
> 重跑后需同步更新主页、PPT 第 6 页、视频口播与社媒帖。

---

## 1. 现象

联网完整重跑一次评测（`tools/batch_run.py` → `tools/benchmark.py`），结果比上次难看很多：

| 指标 | 上次（修复上下文丢失后第一次复测） | 本次完整重测 |
|---|---|---|
| MAE 平均绝对误差 | 13.33 | **20.44** |
| 误差 ≤5 分占比 | 22.2% | **0.0%** |
| 证据可溯源率 | 95.1% | **84.9%**（135/159） |

逐份看更刺眼：人工打分 93 / 95 / 95 的 S08 / S09 / S10，系统只给了 60 / 60 / 55；
而 S08 在上一次跑分里是 100 分。

## 2. 排查过程

第一步是排除「是不是我前一天加的 JSON 修复把引用改坏了」。做法：把新旧两批 `batch.json`
的每一条 quote 拿回原文做匹配，并分类统计失败原因。

结论：**不是 JSON 修复引起的**。失败的 quote 里没有转义残留、也没有被截断的痕迹，
而且新旧两批里有完全相同的失败样本（例如 S09/r5、S10/r3），说明问题一直存在。

真正的原因有两类，都很具体：

### 根因一：PDF 抽取把正文切得满是断行

| 报告 | 来源 | 平均每隔多少字一个换行 |
|---|---|---|
| S08 / S09 / S10 | PDF | **18.9** |
| S01 | DOCX | 25.3 |

PDF 转出来的文本几乎每行都斩断。模型看到的是"客户端 Windows 上的 VDS 3.9，路径 D:\VDS\VDS.exe"
这样通顺的句子，而原文里这句话中间夹着换行与多余空格——**逐字匹配必然失败**。

典型失败样本（去掉空白后就匹配得上了）：

```
[S08/r2] "客户端 Windows 上的 VDS 3.9，路径 D:\VDS\VDS.exe"
[S09/r2] "所有脚本固定 SEED=42，并输出 JSON 指标、CSV 预测和数据元信息。"
[S10/r4] "最终平均交叉熵 0.008738"
```

如果把正文与引用**同时**做空白归一（两侧用同一套规则），本批次的可溯源率是
**155/159 = 97.5%**，而不是 84.9%。

### 根因二：短引用「一票否决」整条判定

`verify_evidence` 里有一条 `min_len = 6`：引用短于 6 个字就算不合法。
本批次有 10 条这样的引用：

```
'实验感想'  '实验建议'  '程序代码'  '设计思路'  '类设计说明'
'运行结果'  '截图说明'  '优点：'  '缺点：'  '执行失败。'
```

问题不在这些引用本身——它们确实是原文里的章节标题。问题在**我们的处理太粗暴**：
一条不合格，就把整条判定连同另外 3 条合格证据一起作废。

### 后果：11 个评分点被判成 0 分

本批次有 **11 个评分点**走了「两次引用都没通过 → 降级 miss + needs_review」这条路，
分数直接归零。而看它们附带的证据，报告里明明有内容：

| 报告/评分点 | 系统判定 | 它引用的证据（真实存在于报告中） |
|---|---|---|
| S08 / r2 环境与步骤 | 0 分 | VDS 客户端路径、远程数据库连接、SELECT 语句 |
| S09 / r5 分析与总结 | 0 分 | 三分类任务定义、典型错误清单、跨场景迁移结论 |
| S10 / r3 核心实现 | 0 分 | 单层 tanh RNN 代码、前向/反向公式 |
| S02 / r3 核心实现 | 0 分 | 「程序代码」「设计思路」等章节标题 |

也就是说：**这套机制在惩罚"报告写得好、模型引用得多"的报告**——
引用越多，越容易撞上一条不合格的，整条判定就越容易被清零。这解释了为什么
人工 93/95/95 的三份 PDF 报告被系统打到 60 分上下。

## 3. 这算不算「放宽规则让数字变好看」？

这是必须讲清楚的问题，因为我们的第二条铁律写的就是——
**绝不放宽匹配规则让数字变好看，正确动作是改 prompt 或缩短引用长度。**

我的判断是：这两处属于**工程缺陷**，不属于"放宽规则"，理由是：

- 空白归一改动的是**输入端**（PDF 抽取产生的换行是抽取artifact，不是报告内容），
  两侧用同一套规则做规范化，仍然是精确匹配，不是模糊匹配；
- 「一条短引用否掉整条判定」改的是**判定的粒度**，改成"逐条校验、剔除不合格的那条、
  只要还剩合格证据就算通过"，规则本身没有变松——引用的逐字匹配要求一行没改。

但我同时承认：**两处修完，分数一定会上升，而且是在 gold set 解封之后修的**。
这一点无法自证清白，只能靠如实披露来交代。所以下一步要不要修，我不自己拍板。

## 4. 三个候选方案

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **A · 只披露不修** | 主页、PPT、视频统一挂 20.44 / 0% / 84.9%，把本文作为已知缺陷公开 | 数字最难看，但最无可指摘；产品本身仍有判死好报告的问题 |
| **B · 修完再披露** | 空白归一 + 短引用不再一票否决 → 重跑 → 挂新数字，并在主页显著位置写明"此修复发生在 gold 解封之后，是靠系统性低估这个信号查出来的" | 分数会上升，容易被质疑；但只要披露到位，与 bug #1 的处理方式一致 |
| **C · 两个数字都给** | 对外主指标用修复前的 20.44（当前系统的真实水平），另附一处"缺陷修复后复测：XX 分"，注明修复时间与动机 | 最诚实，也最花时间；评委看到的是两个数字和一份取舍说明 |

## 5. 如果决定修，实施要点

1. `parser.py`：解析后对正文做一次空白归一（`re.sub(r'\s+', ' ', text)`），
   模型上下文与原文校验使用同一份规范文本；章节切分仍在原始文本上做，
   `char_start/char_end` 归一后重算（否则详情页定位会错位）。
2. `llm.verify_evidence`：改为**逐条**判定——剔除不合格的引用后，若仍剩下
   至少一条合格引用，则判定成立，并把被剔除的那条记进 `reason`；
   长度阈值 `min_len` 保持 6 不变。
3. 改完**完整重跑** `batch_run.py` + `benchmark.py`，把新数字同步到
   主页 `METRICS`、PPT 第 6 页、视频口播、社媒帖；**不沿用旧值**。
4. 在主页与 PPT 写明修复时间、触发原因（"系统性低估"这个信号），
   以及"我们无法自证这个修复没有沾到 gold 的光"。

> 一句话：发现问题是本事，承认修完会涨分也是本事。**只做一半都不算数。**

## 6. 实际改了什么（2026-09-22）

| # | 位置 | 改动 |
|---|------|------|
| 1 | `parser.canonical()` / `parse_file()` | 正文统一做空白归一（`re.sub(r"\s+", " ", text)`）。章节切分仍在**原始文本**上做（识别标题需要换行），切完再各自归一并按归一文本重算 `char_start/char_end`，保证详情页定位不错位 |
| 2 | `llm.verify_evidence()` | 改为**逐条**判定：不合格引用剔除，还剩至少一条合格引用即判定成立；保留的引用仍须逐字存在于原文。被剔除的写进 `reason` 留痕 |
| 3 | `models.ItemJudgement.dropped_quotes` | 新增字段（模型不输出），专门存被剔除的引用 |
| 4 | `tools/batch_run.py` | details 增加 `dropped` 字段 |
| 5 | `tools/benchmark.py` | 正文改用 `parser.canonical` 后再匹配（否则等于自己给自己制造失败）；被剔除的引用计入分母且算不可溯源——**保证可溯源率仍按「模型原始产出」计算，不因筛选而虚高** |
| 6 | `app.py` / `batch_ui.py` | 两处原本绕过 `parse_file` 直接 `open()` 读文本的地方，统一改走 `parse_file`，避免界面与批量评测用的正文不一致 |

离线验证：上一轮 14 条失败引用中，空白归一救回 **9 条**（S08 3/3、S10 4/5、S09 2/5）；
其余 5 条属于模型自行改写（例如把 SQL 重排了格式），现在会被逐条剔除而不再拖累整条判定。
章节偏移自洽性检查：33 个章节全部能在归一文本中找到，偏移单调递增。
