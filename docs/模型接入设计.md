日期：2026-09-24
涉及文件：`providers.py`（新增）、`llm.py`、`selfcheck.py`、`app.py`

## 一、需求与一个必须先说清的事实

> 学生自己选择接入的 API，同时保留一个默认的、不用手动接入的免费通道。

**必须先说清**：不存在真正免费、无需注册、无限额、可商用的通用大模型 API。
所谓「免费 API」要么有额度上限，要么随时会挂，要么不允许商用。

所以「默认免费通道」我给出的答案是**离线规则引擎**，而不是某个第三方免费接口：

| 方案 | 判断 |
|---|---|
| 挂一个第三方免费模型 | ❌ 随时失效、有速率限制、条款多半不允许教学商用，出问题整站瘫痪 |
| **默认 = 离线规则 8 项（58 权重）** | ✅ 零配置、零成本、永不失效、结果可复现，且我们已经做扎实了 |
| 平台共享额度（管理员配 key） | ✅ 可选，学生免配置，但**必须带限额**，否则一个公开链接就能刷爆账单 |

于是形成三层通道：

```
① 离线规则（默认·永远可用·免费）  →  8 项 / 58 权重
② 平台共享额度（可选·管理员配）    →  12 项 / 100 权重，带每日限额
③ 学生自带密钥 BYOK（推荐）        →  12 项 / 100 权重，花学生自己的钱
```

**任何一层失败，都会自动回落到 ①，绝不让学生的体检中断。**

## 二、架构：配置只沿调用链传递，绝不落全局

这是本设计最重要的一条，也是最容易写错的地方。

直觉写法是「界面把配置写进一个模块级变量，调用方去读」，但 **Streamlit 多个会话
共享同一份模块**：那样做等于 A 同学填的密钥会被 B 同学的会话用掉 ——
既是安全事故，也是计费事故。

所以改成显式传参，全程无全局状态：

```
侧边栏 render_llm_picker()
        │  返回 dict（只存在于当前会话）
        ▼
SC.run_selfcheck(..., llm_cfg=cfg)
        ▼
SC.ai_check(..., llm_cfg=cfg)
        ▼
llm.call_json(..., api_key=..., base_url=..., model=...)
        ▼
llm._get_client(timeout, api_key=..., base_url=...)
```

`llm.py` 里原有的环境变量读取逻辑**一点没动**：参数为 `None` 时仍读环境变量，
教师评阅链路（`pipeline.py`）完全不受影响。

回归测试 `test_api_key_is_passed_explicitly_not_stored_globally`
与 `test_two_different_keys_do_not_leak_between_calls` 锁死这条纪律。

### 3.4 采样参数的厂商差异（Kimi 温度事件）

同一套 OpenAI 兼容协议，各家对**采样参数**的容忍度并不相同。这一点
不看官方文档是发现不了的，而踩中的表现又极具迷惑性：**两条通道一行代码
没改，DeepSeek 正常、Kimi 必挂**。

依据 Kimi 官方《模型参数参考》
（`platform.kimi.com/docs/api/models-overview`，表中「固定」即不可修改）：

| 参数 | kimi-k2.6 / k2.7-code / k3 | DeepSeek 等多数厂商 |
|---|---|---|
| `temperature` | 固定值（思考 1.0 / 非思考 0.6） | 接受任意合法值 |
| `top_p` | 固定 0.95 | 接受 |
| `n` | 固定 1 | 接受 |

而本流水线为了评分可复现，一贯传 `temperature=0.0`（见 `pipeline.py`
重试判定与 `selfcheck.py` 的 AI 体检）。于是：

- DeepSeek：接受 0 → 正常；
- Kimi k2.6：拒绝 0 → `400 invalid_request_error`，界面只看到「跑不出来」。

处理办法在 `llm.temperature_allowed()`：**按模型名决定这个参数发还是不发**，
不是传默认值、也不是传 None，而是整个参数都不传（交还平台自己的固定值）。
由 `FIXED_TEMPERATURE_PREFIXES` 维护，其余厂商不受影响。

**代价必须写清楚**：这类模型无法再把评分锁到可完全复现，同一份报告连查
两次可能有几分出入。系统已在自检页就此给出提示，并建议对一致性要求高的
场合改用 DeepSeek。产品定位本来就是「AI 评分只是建议、教师有最终决定权」，
自检看的是问题定位与改进趋势，因此这个波动在可接受范围内 —— 但要如实告知，
不能让学生两次查出不同分数后以为是系统坏了。

回归测试：`tests/test_model_params.py`；
端到端（真实 HTTP + 真实 SDK）：`tools/verify_kimi_fix.py`。

### 3.5 排障：先用「测试连接」，别急着猜

侧边栏配置完成后会有一个**🔌 测试连接**按钮，它真实调用一次接口并输出：

1. 用当前 Key 拉取可用模型列表 → 验 Key 是否有效、端点是否配错；
2. 检查模型名是否在这个 Key 名下 → 换账号 / 未开通时会在这里露馅；
3. 用业务实际的参数打一次最小对话 → 锁定采样参数问题；
4. 验一次 JSON 强输出 → 确认该型号支持 `response_format`。

逐步编号输出，**整段可复制**，且密钥已被 `llm._strip_secret` 全部替换
（连末 4 位都不留 —— 与界面回显 `mask_key` 保留末 4 位是两个标准，别混淆）。
第 3 步故意沿用真实参数，因此「② 通、③ 不通」即可直接判定为采样参数问题。

**Kimi 还有一个高频坑**：国内站（`platform.moonshot.cn` → `api.moonshot.cn/v1`）
与国际站（`platform.kimi.ai` → `api.moonshot.ai/v1`）的 Key **互不通用**，
打错站点只会得到一句 401。诊断结论里已经写了这一点。

## 四、三条安全纪律

1. **密钥只存 `st.session_state`** —— 不落盘、不进日志、不进导出文件。
   会话结束即消失。
2. **回显一律脱敏** —— `providers.mask_key()` 只留末尾 4 位。
   界面提示、导出摘要都用 `providers.describe()`（已脱敏）。
3. **异常消息要过滤密钥** —— 某些供应商的网络异常会把请求 URL（含 key）
   带进错误消息。`ai_check` 在写入 issue 前会做替换：

   ```python
   secret = (llm_cfg or {}).get("api_key") or ""
   if secret and secret in msg:
       msg = msg.replace(secret, providers.mask_key(secret))
   ```

   测试 `test_error_message_never_leaks_key` 锁死。

## 五、降级行为（沿用既有硬约束）

| 情况 | 行为 |
|---|---|
| 选了离线通道 | 4 项判「未检测」，提示可去左侧接入模型 |
| 配置不完整（缺 key / URL / 模型） | **不发起调用**，直接判「未检测」并说明缺什么 |
| 调用失败 / 超时 / 401 | 判「未检测」，原因写进结果（密钥已脱敏） |
| 平台额度用完 | 自动回落离线规则，提示剩余次数 |

**未检测项一律从总分分母中剔除，绝不当成 0 分算给学生。**

「配置不完整就不发起调用」是特意加的：否则学生要等 60 秒超时
才看到一句看不懂的报错。

## 六、平台共享额度（可选）

管理员在 `.env` 里配：

```bash
ENABLE_SHARED_AI=true
SHARED_LLM_API_KEY=sk-...
SHARED_LLM_BASE_URL=https://api.deepseek.com/v1
SHARED_LLM_MODEL=deepseek-chat
SHARED_DAILY_LIMIT=20
```

两个条件必须同时满足才生效：`ENABLE_SHARED_AI=true` **且** key 非空。
只配 key 不开关 = 不生效（测试 `test_shared_channel_requires_explicit_opt_in` 锁死）。

当前限额是**会话内计数**，够 demo 用。**生产环境必须把限流做在服务端**
（按学号 / IP），否则刷新页面就能绕过。

## 七、两套链路的接线方式（2026-09-24 补齐）

选好通道只是「配置合法」，「配置真的被用上」是另一件事 —— 这里出过一次事故，
所以单独记清楚。详见 `docs/bugfix-密钥未透传.md`。

```
侧边栏 render_llm_picker() → llm_cfg
   │
   ├─→ 学生自检：run_selfcheck(..., llm_cfg=llm_cfg) → ai_check(..., llm_cfg) → call_json(**_kw)
   │
   └─→ 评阅：run_grading(..., llm_cfg=llm_cfg)
                └→ stage_rubric / stage_judge / stage_consistency / stage_feedback
                       每处 call_json(**_kw)   ← _kw = providers.llm_kwargs(llm_cfg)
```

**唯一的翻译点**是 `providers.llm_kwargs(cfg)`：

| 输入 | 返回 | 含义 |
|---|---|---|
| `None` | `{}` | 调用方没指定（CLI / 批量脚本）→ 退回环境变量 |
| `{"id": "offline"}` | `{}` | 纯规则通道 → 不显式传密钥 |
| 配置残缺 | `{}` | 宁可不传，也不塞半成品密钥 |
| 有效配置 | `{api_key, base_url, model}` | 显式透传 |

**`DEMO_MODE` 与自带密钥的关系**（两处判断必须一致）：

| 场景 | 行为 |
|---|---|
| `DEMO_MODE=true` + 无显式密钥 | 拦截，返回预置演示结果；没有预置结果则报错并给出两条出路 |
| `DEMO_MODE=true` + 学生自带密钥 | **放行**（是他自己的账户，不是「偷偷烧平台的钱」） |
| `DEMO_MODE=false` | 正常调用；无显式密钥就用环境变量里的平台配置 |
| 显式选 offline 却跑评阅 | 当场拒绝并指路（评阅链路没有纯规则版本，不能静默退化） |

## 八、耗时与提速（2026-09-24 增补）

用户反馈「Kimi 特别慢」。耗时只有两项构成：**单次调用多慢** × **调了多少次**。
前者取决于模型（思考模式、平台排队、网络），我们能改的是后者，外加一个厂商开关。

### 8.1 关掉 Kimi k2.6 默认开启的思考模式

`kimi-k2.6` 默认 `thinking = enabled`：先写一大段推理再作答，单次调用慢数倍。
已在 `llm.fast_params()` 里按型号下发 `{"thinking": {"type": "disabled"}}`，
走 `extra_body`（OpenAI SDK 不认识这个字段，当关键字传会 `TypeError`）。

**必须精确到型号，不能按 `kimi-` 前缀一刀切**（与 3.4 的 temperature 是同一个坑）：

| 型号 | 能否关 | 依据 |
|---|---|---|
| `kimi-k2.6` | ✔ 可关 | 支持 `disabled` / `enabled` / `enabled+keep` |
| `kimi-k2.7-code` | ✘ | 只接受 `enabled`，传 `disabled` 会报错 |
| `kimi-k3` | ✘ | 官方参数表该行为「—」，没有这个参数 |

一刀切会把「慢」治成「跑不起来」—— 比不优化更糟。
`tests/test_model_params.py` 用 4 个型号的参数化用例钉住了这一点。

### 8.2 A 阶段并发

每个评分点一次判定（判定失败还要重跑），开了复核再加一次 —— N 个评分点串行就是 N 倍等待。
`pipeline.run_grading(..., judge_workers=4)` 改用线程池并发，默认 4 路。

- **取 4 而不是更高**：并发越高越容易撞平台的每分钟请求数限制（429），
  退避重试反而更慢。界面给了 1~8 的滑块，让学生自己看着调。
- **并发的头号风险是静默错配**：各评分点耗时不同，若按「完成顺序」回填，
  第 1 个评分点的判定会贴到第 3 个上 —— 不报错、不降分，只是理由对不上号，
  一旦发生就会被当成正确结果采信。实现按**原始下标**回填，`ex.map` 按输入顺序产出，
  并用 `ShuffledExecutor`（倒序产出的假线程池）做了反向对照。

### 8.3 界面上的「⚡ 速度与质量」

评阅页新增折叠块：

- **一致性复核开关**（默认关）：开着每个评分点多一次调用，耗时约翻倍；
  关掉只剩一次判定。结果与导出里都会如实记录这次究竟跑没跑复核。
- **并发路数滑块**（默认 4）。
- 生成评分点后直接显示**预计调用次数**，让人在点之前就知道要等多久。

### 8.4 实测

`python tools/bench_speed.py` —— 固定单次调用耗时，测的是**调用编排**的差异，
不测网络抖动（绝对值没有参考价值，倍数才有）：

| 配置 | 调用次数 | 相对改动前 |
|---|---|---|
| 串行 + 开复核（改动前） | 17 | 1.00× |
| 串行 + 关复核 | 9 | 1.67× |
| 并发4 + 开复核 | 17 | 3.00× |
| **并发4 + 关复核（当前默认）** | **9** | **4.99×** |
| 并发8 + 关复核 | 9 | 7.46× |

## 十、待确认

1. **要不要默认开启平台共享额度？** 开启则学生开箱即用但平台承担费用；
   关闭则学生必须自带 key（或只用离线 8 项）。当前默认关闭。
2. **学生密钥要不要记住？** 现在每次刷新都要重填。持久化就得加密存储，
   引入一整套密钥管理，对学生 demo 可能不值得。
3. **Ollama 通道要不要在部署环境里禁用？** 它指向 `localhost`，
   云端部署时学生点了会连不上，应当按部署环境隐藏。
